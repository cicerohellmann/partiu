## What it does

- The pure logic in `lib/utils.ts` (956 lines) that many screens depend on. Write it once in shared Kotlin and port its tests. All functions below are exactly as in the web.
- Dates and times (flight and segment times are UTC instants; trip, stay and rental dates are plain `YYYY-MM-DD` keys):
  - `formatTime(iso, tz)`: 24-hour `HH:mm` using the `en-GB` locale in the given IANA zone (or the device zone if none); empty input gives an em dash.
  - `formatDate`, `formatDayMonth` (day and month without the year, so it is always shorter than `formatDate` of the same value: the full date "26 de set. de 2026" in pt-BR overflowed the fixed-width clock column of a transport row, which is why it exists; empty for a missing, empty or unparseable value, never the words "Invalid Date"; a datetime without a zone such as `2026-09-26T07:25:00` is read as device local time, so it shows day 26; `utils.ts` 50-68), `formatDateLong` (weekday, month, day, year), `formatDateTimeLocale` ("Never" for empty): use the locally stored app language as locale. Web quirk (report upstream, do not copy): `formatDate` does `new Date('YYYY-MM-DD')` (UTC midnight) and formats in the device zone (`utils.ts` 41-48, 85-91), so with a device in America/Sao_Paulo the date key 2026-03-31 prints "Mar 30, 2026" on the trip card; date keys from trips, stays and rentals all go through it. Zones at or ahead of UTC are unaffected. `formatDateRange` joins start and end with " – " and shows one date when end is missing or equal.
  - `formatDuration(minutes)`: null for 0/null, `"2h 15m"` when 60 or more, else `"45m"` (120 gives `"2h 0m"`).
  - `formatTimezone(iso, tz)`: the short zone name (for example "GMT+1") or null.
  - `toLocalInputValue(iso, tz)`: `YYYY-MM-DDTHH:mm` of the instant in the given zone, used to seed edit forms; empty for a null, undefined, empty-string or unparseable instant. Examples: `2026-10-04T00:00:00+00:00` in `Asia/Shanghai` gives `2026-10-04T08:00`, `2026-10-03T20:00:00+00:00` gives `2026-10-04T04:00` (the date rolls with the zone), and `2026-10-04T02:00:00+00:00` in `America/Sao_Paulo` gives `2026-10-03T23:00` (`utils.ts` 114-131). If the IANA zone name is invalid (the `toLocaleDateString` call throws) the result is the first 16 characters of the ISO string, which is the UTC wall time `YYYY-MM-DDTHH:mm` (`utils.ts` 127-130); a null or unset zone uses the device zone; an unparseable instant gives an empty string.
  - `localDateKey(iso, tz)`: `YYYY-MM-DD` of the instant in the given zone. `daysBetweenDateKeys`, `addDaysToDateKey` do date-key arithmetic in UTC.
- Trip status (`utils.ts` 254-267): `inferTripStatus` gives `completed` when an end date exists and the local midnight that ends that day is strictly before now (so a trip that ends today is still not completed), else `ongoing` when a start date exists and its local midnight is at or before now, else `upcoming`. A missing date is simply skipped: only an end date in the past gives `completed`; only a start date in the future, or no dates at all, gives `upcoming`; an end date of today with no start date gives `upcoming`. `timeUntilTrip(start)`: `diff = Date.parse(start) - now`; a date-only `YYYY-MM-DD` start is parsed by the platform as UTC midnight (not local), so the countdown runs to 00:00 UTC of the start date, while a full ISO instant is exact. `days = floor(diff/86400000)`, `hours = floor(diff/3600000) % 24`, `minutes = floor(diff/60000) % 60`; the empty string when diff is 0 or less; by the remaining time (`utils.ts:220-252`): 60 days or more `time.in_months` ("in {n} months", n = days div 30); 30 to 59 days `time.in_mo_d` ("in {mo}mo {d}d", mo = days div 30, d = days mod 30) or `time.in_mo` when d is 0; 1 to 29 days `time.in_d_h` ("in {d}d {h}h") or `time.in_d` when h is 0; under a day but at least an hour `time.in_h_m` or `time.in_h` when m is 0; under an hour `time.in_m` (total minutes, e.g. "in 40m"); under a minute but still in the future `time.now`. A zero second part is dropped ("in 3d", "in 2h", "in 2mo").
- Flight state: `isFlightCancelled` (`status` or `live_status` is `cancelled`; `status` is the airline's own word, written from a cancellation email, and is read as well as the live tracker, and the result does not depend on where the flight sits in time: a cancelled flight whose arrival is long past is cancelled while `flightStatus` still says `completed`, `utils.ts` 190-192), `isFlightRescheduled` (`rescheduled_at` set and not cancelled), `hasScheduleChangeNotice` (`schedule_change_notice_at` set and not cancelled), `flightStatus` (`utils.ts` 211-216: `completed` if an arrival time exists and is before now, else `active` if a departure time exists and is before now, else `upcoming`; a missing arrival falls through to the departure check). `cabinLabel` (`utils.ts` 165-173) maps `economy` to "Economy", `premium_economy` to "Premium Economy", `business` to "Business", `first` to "First Class" (these are English literals, not translated); an unknown value such as `charter` is returned as is, a null or empty value as an em dash "—". `seatMapUrl(aircraft)` (`utils.ts` 269-276) builds `https://flightseatmap.com/aircraft/<slug>-seat-map` where the slug is the type in lower case with each run of characters other than a-z and 0-9 turned into one `-` and leading or trailing `-` removed ("Boeing 737-800" gives `boeing-737-800`, "AIRBUS A320" gives `airbus-a320`); null if the type is null or empty.
- Transport legs: `flightToLeg` and `segmentToLeg` give one leg shape (`kind` `flight` or `segment`, id `flight-<id>` or `segment-<id>`, times, zones, duration, and the source record kept on the leg). The place labels differ: a flight leg uses the IATA codes (`departure_airport`, `arrival_airport`; empty string when missing), a segment leg uses the station names (`departure.name`, `arrival.name`, for example "Beijing West" and "Xi'an North"), so nothing may assume three letters (`utils.ts` 306-336). `splitLegs(flights)` splits a round trip: only when there are 2 or more flights, the first departure airport equals the last arrival airport, and the largest gap between consecutive flights (previous arrival, or its departure when no arrival is known, to next departure) is at least 12 hours; the flight after that gap starts the return. With fewer than 2 flights, a missing airport code, or a trip that ends at an airport other than where it started (a one-way with a long stopover), nothing splits: all flights are outbound and `returning` is null (`utils.ts` 471-510). `splitTransport(flights, segments)` returns `outbound`, `during`, `returning` (null if none) and `hasFlights`: with no flights all segments are outbound; otherwise a segment departing strictly before the outbound ends joins outbound, one departing at or after the return start joins return, the rest are during. "Outbound ends" is the latest arrival among the outbound flights (a flight with no arrival uses its departure), so a segment that departs while the outbound flight is in the air joins outbound; "return start" is the earliest departure among the return flights. When there is no return nothing can join it: every segment departing at or after the outbound end is during (a one-way trip's train after landing is during), and `returning` stays null (`utils.ts` 370-415). `connectionInfo(prev, next)` returns `gapMin` (next departure minus previous arrival, rounded to whole minutes), `label` ("2h 30m" for 150 minutes; "2h 0m" for exactly 120; only minutes, "45m", under an hour) and `place` (the previous leg's arrival place label: an IATA code after a flight, a station name after a segment) or null when the previous arrival or the next departure is missing or the gap is zero or negative (`utils.ts` 516-526). `dateDividerInfo` returns `{label, crossesDay: true}` when the calendar date changes between legs, judged by the first 10 characters of the ISO strings: the previous leg's arrival (its departure when it has no arrival) against the next leg's departure; it returns null when the dates are equal, when either is missing, or when the next leg has no departure. The label is the next departure as short weekday, short month and day number without a year (for example "Sun, Jun 2"), in the app language and in the next leg's departure zone (the device zone when it has none); if that formatting throws the label is the first 10 characters of the departure string (`utils.ts` 532-561). `legStats` returns `flyingMinutes` (sum of the leg durations, a missing duration counting as 0) and `totalMinutes` (first departure to last arrival, rounded to whole minutes; 0 if any stopover between consecutive legs exceeds 24 hours, if the first leg has no departure or the last no arrival, or if the list is empty, in which case `flyingMinutes` is 0 too; `utils.ts` 423-448). There are no distance totals in this file.
- Day logic: `localDateKey(iso, timezone)` is the calendar date of the instant in the given IANA zone, formatted with the `en-CA` locale (so `YYYY-MM-DD`, sortable as text), null for an empty input, and falling back to the first 10 characters of the ISO string if the zone lookup throws (`utils.ts:766-779`). A flight is dated in its departure and arrival airport zones (`departure_timezone`, `arrival_timezone`), a ground segment in each place's `timezone`. `legDateKeys(from, to)` lists every local date key from the departure day through the arrival day (for example 2026-12-31 to 2027-01-02 gives 2026-12-31, 2027-01-01, 2027-01-02; just the departure day when `to` is missing, equal to or not after `from`, so a mistyped earlier year never gives a backwards or decades-long range; an empty list when `from` is null; capped at 366 keys), `legRoleFor(date, from, to)` gives `departs` on the first day, `arrives` on the last day, `transit` strictly between, else null (and null with no `from`); a leg that starts and ends on the same day, or whose `to` is missing or not after `from`, gives `departs` on that day and never `arrives` (the first-day check runs first), `staysForDay` (nights, check-ins, check-outs), `rentalsForDay` (held, pickups, drop-offs; unlike stays it is inclusive of the drop-off day, so a 29 March to 1 April hire is held on four days and its last day reads "day 4 of 4"; a day is held when `pickup_date` <= day <= `dropoff_date`, "day N" is days since `pickup_date` plus 1 and "of M" is `dropoff_date` minus `pickup_date` plus 1, so the backend's own `days` field is ignored (a rental stored with `days: 3` for 29 March to 1 April still reads "day 4 of 4"); a same-day hire reads "day 1 of 1"; `pickups` and `dropoffs` list the rentals whose `pickup_date` or `dropoff_date` equals the day; `utils.ts` 845-863), `stayNightCount` (the backend `nights` field whenever it is not null, so a stored 0 stays 0, otherwise `check_out_date` minus `check_in_date` in days; `staysForDay` bands "night N of M" with N = days since check-in plus 1 and M = `stayNightCount`, on every date d with check_in_date <= d < check_out_date; the check-out day is a departure day, not a night; on a changeover day (one stay's check-out is another's check-in) the day lists the first stay under check-outs only and the second under both check-ins and nights; a day-use booking with the same check-in and check-out date and `nights` 0 lists the stay under both check-ins and check-outs and has no night), `splitTransport` sorts each bucket ascending by departure instant, with legs that have no or an invalid departure last (`utils.ts:337-346`), `accommodationGaps(stays, tripStart, tripEnd)` (the date keys from the trip start up to and including the night before the trip end, so the last day of the trip is never a night, that no stay covers, a stay covering a date when `check_in_date` <= date < `check_out_date`; a stay 4-8 June with a trip 4-8 June gives none, with a trip starting 3 June gives `2024-06-03`; an empty list when the trip has no start or end date or when there are no stays at all, because "every night is missing" is no use to someone who has not started booking; `utils.ts` 893-908), `stayOutsideTravel(stay, flights, segments)` (`utils.ts` 933-956) returns `before`, `after`, `overruns` or null. It collects the departure and arrival instants of every flight and every ground segment, keeps the non-empty ones, takes the first 10 characters of each stored UTC string (a date, not converted to a local day, on purpose: a day of slack is fine for "is this booking in the wrong month?") and sorts them: `first` and `last`. With no dates at all it returns null. Otherwise: `before` when `check_out_date` < `first`; else `after` when `check_in_date` > `last` (this wins over `overruns`, which is also true of such a stay); else `overruns` when `check_out_date` > `last`; else null. It is deliberately one-sided: a check-in before the first departure is never flagged (the night before an early flight is a normal airport-hotel booking) and a check-out on the very day of the last arrival passes. Ground segments count as transport too. The result only drives a warning, never a refusal.
- Money: `formatCurrencyTotals` returns `"CODE amount"` strings sorted by code (whole numbers without decimals, others with exactly 2: `{SEK: 900, EUR: 420}` gives `EUR 420`, `SEK 900`; 420.5 gives `EUR 420.50` or `EUR 420,50`, because the web calls `toLocaleString()` with no locale, so the decimal and thousands separators follow the device region, not the app language; native does the same); an empty list for no totals (null or an empty map); no conversion anywhere. `budgetLevel(spent, amount)`: null when there is no positive budget, `over` at 100 percent or more, `near` from 80 percent (`BUDGET_WARN_AT = 0.8`), else `under`. `lib/currencies.ts` lists 41 currency codes (the backend's `SUPPORTED_CURRENCIES` rejects any other with 400), offered in this order in every currency picker: AED, ARS, AUD, BRL, CAD, CHF, CLP, CNY, COP, CZK, DKK, EGP, EUR, GBP, HKD, HUF, IDR, ILS, INR, ISK, JPY, KRW, MAD, MXN, MYR, NOK, NZD, PEN, PHP, PLN, QAR, RON, SAR, SEK, SGD, THB, TRY, TWD, UAH, USD, ZAR.
- Trip card summary: `tripContents(flightCount, segmentTypes, stayCount, rentalCount)` returns parts in order flights, train, bus, ferry, car, other legs, stays, rentals (only counts above 0; label keys `trips.flight_count`, `trips.segment_count_train`, `trips.segment_count_bus`, `trips.segment_count_ferry`, `trips.segment_count_car`, `trips.segment_count`, `trips.stay_count`, `trips.car_rental_count`, each with a `_plural` form in en.json; the known ground kinds come in that fixed order whatever the order of `segmentTypes`; an empty trip gives an empty list, not a row of zeros; `utils.ts` 714-755). Icons: ✈ flights, 🚆 train, 🚌 bus, ⛴️ ferry, 🚗 car, "↔" for all unknown ground types together (label `trips.segment_count`), 🛏️ stays, 🚗 car rentals (`trips.car_rental_count`, counted apart from ground legs and last). The UI card (T-009) adds the people 👥 and invites ✉ chips from `tripPeople`. A flight count above 0 is the only way the flights part appears here; the "0 flights" case is the card's (T-009) rule for a trip with no legs, stays or rentals. `tripPeople(collaborators, pendingInvites = 0, guests = 0)` (`utils.ts` 701-712) returns null when all three are 0 (a solo trip is not "1 person"), else `{people: collaborators + guests + 1, pending: pendingInvites}`; the 1 is the owner, who has no share row; guests count as people; pending invitations are never added to `people`, but a trip with only a pending invitation still gives a result (`tripPeople(0, 2, 0)` is `{people: 1, pending: 2}`).

## Native additions (not in web)

- Date keys (plain `YYYY-MM-DD`: trip, stay and rental dates) are shown as the calendar date they are, never shifted by the device time zone. The web shifts them back a day in zones behind UTC (bug, to be reported upstream). Applies to `formatDate`, `formatDayMonth`, `formatDateLong` and `formatDateRange` when given a bare date key.
