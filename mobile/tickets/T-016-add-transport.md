## What it does

Web source line ranges: `AddTransportPage.svelte` 1-180 (logic), 182-440 (markup); `AirportCombobox.svelte` 1-126. The page has no owner, collaborator, admin or demo check; the server enforces access.

- Screen `/trips/{tripId}/add-transport`, titled "Add transport", with a back link to the trip. Reached from the "+ Add transport" button on the trip page (T-014).
- Type picker: five options, Flight (default), Train, Bus, Ferry, Car (radio buttons, 44 px high). Ground types are train, bus, ferry and car only; there is NO "other" type. Departure and arrival date-times, booking reference AND seat are shared and survive a type change. All flight-only fields (flight number, airline name/code, cabin, airports, terminals, gates, passenger, notes) and ground-only fields (from/to places, operator, number) also keep their typed values in memory and reappear when switching back (80-107). Seat is hidden for car and is sent as null for car whatever was typed earlier.
- Trip span: on open the page calls `GET /api/trips/{tripId}`. If the trip has `start_date` and `end_date`, a hint "This trip runs {start} – {end}. Edit the trip's dates to add a leg outside it." is shown, where `{start}` and `{end}` are the raw `YYYY-MM-DD` strings of `trip.start_date` / `trip.end_date` (not locale formatted; the dash is an en dash; 51-53) and the datetime fields get `min = startT00:00` and `max = endT23:59`. The two bounds are independent (`AddTransportPage.svelte:45-53`): the floor is set whenever `start_date` is set; the ceiling is set whenever `end_date` is set unless it is earlier than `start_date` (then there is a floor and no ceiling, because a floor above the ceiling would grey out the whole calendar); the hint needs both dates. With a trip that has no dates the fields have no min and no max at all. The bounds are date-granular (`T00:00` and `T23:59`, never the time of a stored leg) so the first and last day of the trip are fully selectable. A failed lookup is ignored and the pickers are unbounded. The form does not default the date to the trip's start date; the datetime fields start empty. The min/max bounds apply to every datetime field in both modes and are enforced only by the picker's own validation: the `valid` gate and the submit handler do not compare the dates with the trip range (45-50, 144-147). The form keeps no draft: leaving the page (Cancel, back, success) discards everything, nothing is stored locally.
- The Cancel link and the top back arrow both go to `#/trips/{tripId}` (there is no `/history` variant of this screen). Flight mode fields: flight number (required), airline name, airline code (max 3 characters; auto-filled with the first two letters, upper-cased, from the flight number when it matches two letters followed by a digit and the code is still empty), cabin class (select values `''` shown as a dash, `economy`, `premium economy` WITH A SPACE not an underscore, `business`, `first`, labelled Economy / Premium Economy / Business / First via `add_flight.cabin_*`; AddTransportPage 257, `lib/utils.ts` 166; because `cabinLabel` (T-008) only maps `premium_economy`, a flight created on the web as `premium economy` is shown raw on the detail screen; decide whether native keeps the space value to match existing data or normalises), departure airport (required), departure date and time (required), departure terminal, gate, arrival airport (required), arrival date and time (required), arrival terminal, gate, booking reference, seat, passenger name, notes.
- Airport field (`AirportCombobox`): free text; each keystroke sets the value to the trimmed upper-cased text (so a typed 3-letter code works without picking). A search `GET /api/airports/search?q=<text>` runs 250 ms after the last keystroke when the text is not blank; blank clears the list. Suggestions show the IATA code plus the detail text `{airport name}, {country code}` joined by a comma and space (just the name when the airport has no country code; `AirportCombobox.svelte` `formatDetail`), for example `GRU` and `Guarulhos International Airport, BR`; picking sets the value to the IATA code and shows `CODE — city` (em dash, see below). Keys act only while the list is open (`AirportCombobox` 65-81): ArrowDown moves the highlight down and stops at the last item (no wrap); ArrowUp moves up and can go back to nothing highlighted (index -1); Enter picks the highlighted item (it is swallowed only when one is highlighted, otherwise the form submits normally); Escape closes the list. Errors close the list silently. Losing focus closes the list after 150 ms (so a tap on a suggestion still registers, 58-63). The list is shown only when the search returned at least one airport (108); an empty result closes it. The input text starts as the bound value (in edit flight the plain IATA code `GRU`, not `GRU — City`); later changes of the bound value from outside are not copied into the text (20-24); only typing and picking change it. After picking, the text is `${iata} — ${city_name}` (U+2014 em dash; the city part and dash are omitted when the airport has no city), for example `GRU — São Paulo`, while the bound value is just the code; this string is hard-coded in `AirportCombobox.svelte` 81-84, not a locale key. The search query is the raw typed text (not trimmed, URL-encoded), the debounce is 250 ms, and there is no minimum length. Unlike the place picker (T-015) there is no per-field cache and no stale-response guard in the web, so a slow older response can replace newer suggestions (native may add a request counter, listed under Native additions). A free-typed value (for example `Sao Paulo` becomes `SAO PAULO`) is submitted as is with no client-side IATA check; a server rejection shows in the form's red error line. The input carries the HTML `required` flag when the screen asks for it (both airport fields on add transport and edit flight do, with the example placeholders `GRU` and `SCL`), so an empty required airport blocks submission. A suggestion is addressed by position: any new keystroke resets the highlight to nothing. The input accepts at most 60 characters, is monospace, forced upper-case and has autocomplete off (97-104). The API matches code, name and city (server side).
- Sections in order (`AddTransportPage.svelte` 189-441). Always first: "Type" (`segments.type`) holding the five-option picker and, when the trip has both dates, the range hint below it. Flight: "Flight" (`add_flight.section_route`: flight number, airline name, airline code, cabin class), "Departure" (airport 180 px wide, date and time, terminal, gate), "Arrival" (same), "Booking Details" (`add_flight.section_booking`: booking reference, seat, then passenger name below), and an untitled section holding the notes textarea (3 rows, vertical resize). Ground: first section titled with the chosen type name (`segments.type_<type>`) with Operator (`segments.operator`) and Number (`segments.number`), "Departure" (From `segments.from` with the place picker, Departs `segments.departs`), "Arrival" (To `segments.to`, Arrives `segments.arrives`), then "Booking Details" (booking reference, seat unless car). Ground mode has no passenger, notes, cabin, terminal or gate.
- Ground mode fields: operator, number, from place (required, place picker T-015 with the type as `kind`), departs (required), to place (required), arrives (required), booking reference, seat (hidden for car). No notes field in ground mode. Example placeholders (AddTransportPage 217-450): flight number `LA800`, airline code `LA`, airline name `LATAM Airlines`, departure airport `GRU`, arrival airport `SCL`, terminals `A` / `2`, gates `A12` / `B4`, booking reference `ABC123`, passenger `SILVA/JOAO`, notes `Any additional info…` (`add_flight.notes_placeholder`). Seat placeholder is `12A` in flight mode and `Car 3, 12A` (`segments.seat_placeholder`) in ground mode; ground operator `China Railway`, number `G87`, from/to `Station or stop`. Flight number, airline code and booking reference are shown upper-case (display only; the submit already upper-cases).
- Required-field marking: all fields are visible at once, with no "more details" expander or collapsed section (`AddTransportPage.svelte` has no `details` element). In flight mode exactly five fields carry the red asterisk: flight number, departure airport, departure date and time, arrival airport, arrival date and time. In ground mode exactly four do: from, departs, to, arrives. Optional fields in flight mode (terminal, gate, cabin class select, notes textarea) are present and unmarked.
- Validation: the submit button ("Add to trip") is disabled until both datetimes are filled and, for a flight, flight number and both airports are non-blank, or, for ground, both place names are non-blank. Required fields show a red asterisk. There is no check that arrival is after departure. The button shows "Saving…" and is disabled while sending. A server or network error message is shown in red above the buttons; cancel is a link back to the trip.
- Flight submit: `POST /api/flights` with `flight_number` (trimmed, upper-cased), `airline_name`, `airline_code` (upper-cased), `departure_airport`, `arrival_airport` (trimmed, upper-cased), `departure_datetime`, `arrival_datetime` (the naive local `YYYY-MM-DDTHH:mm` strings as typed), `booking_reference` (trimmed, upper-cased), `passenger_name`, `seat`, `cabin_class`, `departure_terminal`, `departure_gate`, `arrival_terminal`, `arrival_gate`, `notes` (all trimmed; empty fields are sent as empty strings, not omitted) and `trip_id`. The web does not call any flight-data lookup here and does not itself fill times, aircraft or status.
- Ground submit: `POST /api/trips/{tripId}/segments` with `{type, departure:{name,lat,lon,country_code}, arrival:{...}, departure_datetime, arrival_datetime, operator, number, booking_reference, seat}` where operator, number, booking reference and seat are trimmed and sent as `null` when empty, and seat is `null` for car. The place objects are sent exactly as the place picker left them (`AddTransportPage.svelte:362-363, 390-391`): `name` is the typed or picked text (not trimmed, only the blank check trims), `lat`, `lon` and `country_code` are `null` for a hand-typed name (a supported case; the leg is then saved without coordinates), and the geocoder's street `address` is not sent by this screen. A ground leg is created with `POST /api/trips/{tripId}/segments` and never calls `POST /api/flights`; a flight never calls the segment endpoint. Datetimes are naive local strings that the backend converts to UTC.
- On success the app navigates to `/trips/{tripId}`.
- Locale keys on this screen: the hint "This trip runs {start} – {end}. Edit the trip’s dates to add a leg outside it." is `add_transport.range_hint` (`AddTransportPage.svelte:52`). The booking section title is `add_flight.section_booking` ("Booking Details", line 409). In flight mode the airport fields are labelled `add_flight.airport` ("Airport (IATA)") and the date-time fields `add_flight.datetime` ("Date & time"), each with the red asterisk (lines 268-303). The ground-mode "To" label is `segments.to` (line 383), the ground number placeholder `segments.number_placeholder` ("G87", line 346), and the type options are `add_transport.type_flight` for Flight and `segments.type_train`, `segments.type_bus`, `segments.type_ferry` and `segments.type_car` for the rest (line 201). The submit button is `add_transport.save` ("Add to trip"), or `add_flight.saving` while sending. Unused by the web: `add_transport.more_details` and `add_flight.save`.

- `GET /api/airports/search?q=` (airportsApi.search)
- `GET /api/stations/search` (via the place picker, T-015)
