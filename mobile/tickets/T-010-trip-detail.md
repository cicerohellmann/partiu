## What it does

- Screen `/trips/{id}`; `/history/{id}` is the same screen, with the back arrow going to History instead of Trips and flight links using the `history` base path. The top bar shows the trip name (`trip.loading`, "Loading trip…", while loading; "Error" if the trip is missing). The back arrow in the top bar has the accessibility label `trip.back` ("Back to Trips").
- Load: `GET /api/trips/{id}` and `GET /api/settings` together (settings failure is ignored). Settings give the Immich URL and whether an Immich API key is set (Immich "configured" = both) and the default currency (fallback `EUR`, passed to budget and expenses). If the trip has an `immich_album_id` and Immich is configured, `GET /api/trips/{id}/immich-album/status` runs and, when the album no longer exists, the album id is dropped locally. Documents and boarding passes are loaded after the trip. For an owner (`is_owner !== false`) `GET /api/trips/{id}/shares` is requested as soon as the trip has loaded (a failure counts as an empty list), NOT when Share is opened, so the People section lists the collaborators and pending invitations without any tap; a collaborator never calls it (`TripDetailPage.svelte:401-404, 556-571`; T-012).
- States: loading screen with `trip.loading` ("Loading trip…"); on error an empty state with the title `trip.load_error` ("Failed to load trip"), the error message as description and a button `trip.back` ("Back to Trips") to Trips (`TripDetailPage.svelte:581-585`); otherwise the page.
- Header: optional cover image (hidden until it loads; one automatic `POST /api/trips/{id}/image/refresh` retry on load error, then hidden; a refresh button inside the cover (so it is only reachable while the cover is visible; title and accessibility label both `trips.refresh_image`, "Find a different image"; `TripDetailPage.svelte:603-611`) calls `POST /api/trips/{id}/image/refresh` for this trip and busts the cache with `?t=`; the list card has no such control, T-009); trip name; date line `📅 {dateRange}` (calendar emoji, space, range; `TripDetailPage.svelte:614-618`); one chips line with flights, ground legs by type, stays, rentals (counts from the loaded sections), people and pending invites (from the trip payload plus the live guest roster; the pending chip uses `trips.pending_invite_count` "{n} invite pending" / `_plural` "{n} invites pending", `TripDetailPage.svelte:243`), the expense total per currency (chip `💰 CODE amount` per currency via `formatCurrencyTotals`, e.g. `💰 EUR 1,234`, seeded from `trip.expenses_total` then updated live when the Expenses section reports), and a budget chip (`🎯 {spent} / {amount}`, each side in `formatCurrencyTotals` form, e.g. `🎯 EUR 700 / EUR 800`; the figures come from the budget panel's `GET /api/trips/{id}/budget` answer (T-027), so it is the viewer's share, and the chip exists only when that answer has both an `amount` and a `currency`; it carries the level `under` / `near` (from 80 percent) / `over` (100 percent or more), so 700 of 800 is `near`, and, unlike the list card, it is shown at EVERY level including `under`; a trip with no budget has no chip; tooltip `budget.hint`, or `budget.hint_shared` when the budget has more than one member; `TripDetailPage.svelte:267-282, 635-644`); airline code badges; booking refs; and for a collaborator "shared by <owner_username>". The whole chips line (including the budget chip) is drawn only when at least one content part (flights, ground legs, stays, rentals), people/pending part or expense-total chip exists; a trip with a budget but none of those shows no budget chip in the header (`TripDetailPage.svelte:621-634`). Order inside the line: contents, people, pending invites, one `💰` chip per currency, then the `🎯` budget chip. There is no status pill, night count or countdown in this header.
- Header contents chips (`tripContents`, `lib/utils.ts:714-758`; built from the loaded rows, so finer than the list card of T-009): `✈ {n} flight(s)` (`trips.flight_count`), then one chip per known ground type in the fixed order train 🚆, bus 🚌, ferry ⛴️, car 🚗, each with its own count (`trips.segment_count_<type>`), then `↔ {n} leg(s)` (`trips.segment_count`) for all other types pooled, then `🛏️ {n} stay(s)`, then `🚗 {n} car rental(s)`. A part whose count is 0 is left out, so the header never says "0 flights" (a trip holding only one stay reads "🛏️ 1 stay"); every label takes the plural twin when n is not 1. A trip with exactly one flight and nothing else reads `✈ 1 flight` (`TripDetailPage.svelte:619-624`).
- Chips line format (`TripDetailPage.svelte:620-652`): one paragraph; its parts are separated by ` · ` (middle dot U+00B7 in a muted `aria-hidden` separator span). A part that is absent leaves no separator. Booking references are drawn below it as one small muted label `Ref: {ref}` per reference, hard-coded English (the web does not use the `trips.ref` key here; that key is only used on the trip card, `TripCard.svelte:233`). Native may localise it with a new key, noted as a deviation.
- Refresh button busy state: while the refresh request runs the button shows `…` instead of `↻` and is disabled. A failure is not handled: nothing is shown and the old image stays (`TripDetailPage.svelte:124-135, 607-610`).
- Delete button busy state: the trip Delete button is disabled while the delete request runs; the confirm dialog closes when the request finishes, whether it succeeded or failed (`finally` block); on failure the error message is shown in a browser alert (`TripDetailPage.svelte:337-350, 726`).
- Rating star labels: each half-star control has the English accessibility label `Rate {n} out of 5` with n = 0.5, 1, 1.5 ... 5, hard-coded in the web, not a locale key (`TripDetailPage.svelte:1147, 1155`).
- Buttons under the header:
  - Edit (T-021): owner only (`is_owner !== false`); a link to `/trips/{id}/edit`, label `trip.edit` ("Edit Trip") with a ✎ prefix. This button row has NO add-transport (or add-flight) button: adding a leg lives only in the Transport section ("+ Add transport", T-014, `/trips/{id}/add-transport`, flights and ground legs through the same entry) and in the empty state below; the web has no separate add-flight route from this page (`TripDetailPage.svelte:665-731`).
  - Calendar export (label `trip.export_ical`, "Export to Calendar", with a 📅 prefix): shown to everyone when the trip has at least one flight; a plain link to `GET /api/trips/{id}/ical` downloaded as `<trip name>.ics`.
  - PDF export (label `trip.export_pdf`, "Export PDF", with a 🖨 prefix): shown when the trip has at least one flight; expands the transport, stays and planner sections and opens the browser print dialog (`window.print`).
  - Printing (`TripDetailPage.svelte:442-466`, `app.css:2592-2660`): before `window.print()` the page expands Transport, Stays and the Planner, waits two animation frames, prints, then restores the previous collapse state. The print layout hides the top nav, tab bar and rail, the button row (`trip-actions`: edit, share, merge, delete, calendar, PDF) and everything marked `no-print` (the Share panel, Documents, Packing, Expenses and Budget card, the shared note, the rating); it forces collapsed-section bodies visible, switches to one column, forces a light theme with near-black text and exact colour printing, and hides the map on Firefox. A native PDF must carry the same content set: header, route chips, Transport, Stays, People, Car rentals, Planner.
  - Immich album button: only when the trip is completed (`inferTripStatus`) and Immich is configured. With a stored album it first checks `GET /api/trips/{id}/immich-album/status` (a failed check counts as existing) and opens the album (deep link `immich://album?id=...`, falling back after 1.5 s to `<immich url>/albums/<id>` in a new tab); with none, or if the album is gone, it calls `POST /api/trips/{id}/immich-album`, stores the returned `album_id` and opens it. Errors show under the button. Details (`ImmichAlbumButton.svelte:12-90`): one secondary button, disabled while creating or checking; label `immich.creating_album` ("Creating album…") while busy, `immich.open_album` ("Open Immich Album ↗") when an album id exists, else `immich.create_album` ("Create Immich Album"). Click calls preventDefault and stopPropagation. Fallback: set `immich://album?id=<id>`, wait 1500 ms; if the page became hidden (visibilitychange, meaning the Immich app took over) cancel the fallback, otherwise open `<base>/albums/<id>` in a new tab with noopener; `<base>` is `immich_url` with trailing slashes removed. A create error is small red text under the button, cleared on the next click.
  - Owner only: Share (toggles the invite panel, T-012), Merge, Delete. Non-owner instead sees "Leave" (T-012).
- Delete: confirm dialog ("trip.delete_confirm", danger style), then `DELETE /api/trips/{id}`, then goes to `#/`. A failure shows a browser alert. The trip goes to the trash (T-034).
- Merge: the button reads `trip.merge` ("Merge into…", with a ⇄ prefix). It opens a dialog titled `trip.merge_title` ("Merge into another trip") with the text `trip.merge_description` ("All flights from this trip will be moved to the selected trip. This trip will then be deleted."); it loads `GET /api/trips`, lists trips other than this one that the user owns (`is_owner !== false`) in a select; confirm is disabled until one is chosen; `POST /api/trips/{id}/merge` `{target_trip_id}` then goes to `#/trips/{target_trip_id}`. Loading (`trip.merge_loading` "Loading trips…"), "no trips" (`trip.merge_no_trips` "No other trips available to merge into.") and error messages are shown in the dialog; the select's first, empty option reads `trip.merge_select_placeholder` ("Select a trip…"); the confirm button reads `trip.merge_confirm` ("Merge") and `trip.merge_merging` ("Merging…") while the request runs (`TripDetailPage.svelte:1211-1259`); the backdrop closes it.
- Empty trip: when there are no flights, ground legs or stays, an empty state titled `trip.empty` ("No transport in this trip yet") with an "Add transport" button (`trip.add_transport`) to `/trips/{id}/add-transport`; a trip with no flights, legs or stays and also no companions and no expenses draws no contents chips line (and so no budget chip, see the chips line rule above). The map (T-013) shows only when there is at least one flight or ground leg.
- Sections: Transport, Stays, People, Car rentals, Day planner and Packing have a header that toggles collapse (chevron ▲ open / ▼ collapsed); Documents, Expenses, the note and the rating do not. Collapse state is in memory only (per visit, all start expanded, nothing persisted). Collapsed bodies are hidden with CSS but stay mounted, so their data is still loaded. The page has exactly two columns of sections. Main column (the "spine"), in order, with these English headings: `trip.transport` "Transport", `stays.title` "Stays", `trip_people.title` "People", `car_rentals.title` "Car rental", `planner.title` "Day Planner" (only when the trip has a start and an end date) and `trip.documents` "Documents". Side column (the "aside"), in order: `packing.title` "Packing List", `expenses.title` "Expenses", `trips.note_label` "Trip notes" and `trips.rating_label` "Trip rating". People belongs to the main column, not the side column, because its guest roster bounds the expense payer and split pickers; Documents is the last card of the main column. No section of one column appears in the other (`TripDetailPage.svelte:836-1180`). Transport (T-014). Collapsed summary, shown under the Transport title only while collapsed and only when the trip has flights: for a completed trip airports chained `GRU → CDG → LHR · N flights` (airports walked in leg order, a repeated consecutive airport is dropped; "flight"/"flights" by plural keys. The web template prints the number twice, "3 3 flights", because `trips.flight_count` = "{n} flight" already contains it (`TripDetailPage.svelte:501-502`); a native build prints "3 flights" once); otherwise flights sorted by departure: if one is in the air (departure <= now < arrival) `✈ <flight_number>  DEP → ARR` (two spaces); else the first future departure `Next: <flight_number>  DEP → ARR  <timeUntilTrip>` (key `trip.next_flight` = "Next"; countdown omitted when empty); else nothing (for example all flights past but the trip not completed). Ground legs are ignored: a trip with only trains or buses shows no summary. Then Stays (T-022), People (T-012), Car rentals (T-023), Day planner (T-024; only when the trip has both a start and an end date; collapsed it shows only the focus day: upcoming trip = start_date, completed = end_date, ongoing = today's local date key if start_date <= today <= end_date, else start_date), Documents (T-011). Side column: Packing list (T-025), Expenses with the Budget panel above the expense list (T-026, T-027), the shared note, the rating. From 1000 px wide the web lays these out as two columns (main column about 1.7 fr, side column 1 fr); below 1000 px it is a single flow where Documents comes first (CSS order 1), the shared note and rating last (order 2) and the other sections in source order (`app.css:2189-2240`).
- Rating (`PUT /api/trips/{id}/rating` `{rating}`): the section heading is `trips.rating_label` ("Trip rating"); the stars and the Clear button sit on the same row as that heading (the rating card has no body of its own; `TripDetailPage.svelte:1120-1178`); five stars, each with a left half (star - 0.5) and a right half (star); tapping a value equal to the current rating sends `null`; the star display updates immediately (optimistic), the failure is not handled. A "clear" button (`trips.rating_clear`, "Clear rating") appears when a rating exists and sends `null`. On touch, dragging across the stars previews a half-step value (0.5 to 5) and releasing sets it. Anyone who can open the trip can rate.
- Shared note: heading `trips.note_label` ("Trip notes"), a 4-row text area with placeholder `trips.note_placeholder` ("Add notes visible to everyone on this trip…"); each edit updates the text and, after 800 ms without typing, saves `PUT /api/trips/{id}/note` `{note}` (an empty text sends `null`); shows "…" while saving and `trips.note_saved` ("✓ Note saved") for 2 seconds. Available to collaborators too.
- Not called by any screen: `POST` / `DELETE /api/trips/{tripId}/flights/{flightId}` exist in the client.

## API calls

- `GET /api/trips/{id}` (tripsApi.get)
- `GET /api/settings` (settingsApi.get; Immich and default currency)
- `DELETE /api/trips/{id}` (tripsApi.delete)
- `POST /api/trips/{id}/image/refresh` (tripsApi.refreshImage)
- `POST /api/trips/{id}/immich-album` (tripsApi.createImmichAlbum)
- `GET /api/trips/{id}/immich-album/status` (tripsApi.checkImmichAlbum)
- `PUT /api/trips/{id}/rating` (tripsApi.setRating)
- `PUT /api/trips/{id}/note` (tripsApi.setNote)
- `GET /api/trips` (tripsApi.list, for the merge list)
- `POST /api/trips/{id}/merge` (tripsApi.merge)
- `GET /api/trips/{trip_id}/ical` (opened directly by the page, not through the API client)
- Used by sections on this page: `GET /api/trips/{id}/shares` (owner only, T-012), documents and boarding passes (T-011), `DELETE /api/trips/{id}/leave` (sharesApi.leaveTrip, T-012).
- Defined in the web client but not called by any screen: `POST` and `DELETE /api/trips/{tripId}/flights/{flightId}` (tripsApi.addFlight, removeFlight).

## Android notes

Calendar export: download the `.ics` with the system `DownloadManager`/Ktor and open it with `Intent.ACTION_VIEW` (MIME `text/calendar`), or insert events directly through `CalendarContract` after asking for `WRITE_CALENDAR`. Prefer the file hand-off for parity with the web app (the user chooses the calendar app). Share the trip with the share sheet using a link to the web UI if wanted later.

## iOS notes

Calendar export: save the `.ics` to a temp file and present it with `UIActivityViewController` or open it so Calendar imports it; direct creation with EventKit needs `NSCalendarsFullAccessUsageDescription`. Prefer the file hand-off for parity.
