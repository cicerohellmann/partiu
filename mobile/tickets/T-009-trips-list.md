## What it does

- Home screen (`/trips`), with the top bar title string `trips.title` (English "✈ My Trips", with the plane glyph) and a "new trip" action (`trips.btn_new_trip`, "+ New trip") linking to `/trips/new` (T-020). It loads `GET /api/trips` (response `{trips: [...]}`) and `GET /api/sync/status` together; a failure of the status call is ignored (status stays null), a failure of the trips call shows the error state. A null or empty response, or one without `trips`, is treated as an empty list (not an error), also for the reload after an upload or a sync (`TripsListPage.svelte` 34, 76).
- States: loading screen with "trips.loading" text; on error an empty-state with a warning icon, the title "trips.load_error", the error message as description and a Retry button that reloads; otherwise the list. Retry and first load both show the loading screen again.
- The list shows trips whose `inferTripStatus` (T-008) is not `completed`, in the order the server returned them; completed trips only appear in History (T-028). When no such trip exists (including a user whose trips are all completed) it shows an empty state with the text "trips.empty_title" / "trips.empty_desc" and three buttons: New trip (`trips.btn_new_trip`), View history (`trips.view_history`) and Settings (`trips.go_settings`, "Go to Settings"; `TripsListPage.svelte:208-218`).
- Chip keys (`en.json`, with `_plural` twins chosen when n is not 1, so 0 is plural): `trips.flight_count`, `trips.stay_count`, `trips.car_rental_count`, `trips.people_count` ("{n} person" / "{n} people"), `trips.pending_invite_count`, `trips.segment_count*`; every placeholder is `{n}`. Chip order: flights, ground legs, stays, car rentals, people, pending invites (`TripCard.svelte` 83-130).
- Each trip is one card, a link to `/trips/{id}`: cover image (lazy; empty alt text, decorative, no accessibility label; loads lazily and asynchronously, `TripCard.svelte` 201-209), name, then, only when the trip has a start date, a meta line with the date range (T-008 `formatDateRange`), the route, and content chips. Below: booking references (`trips.ref`, "Ref: A, B"; the references joined with ", " in one label, and no label at all when the list is empty or missing; `TripCard.svelte:133, 231-235`), the rating stars, expense totals and a budget alarm. The card has two slots filled by its host screen: a required badge (on this list the status pill) and an optional footer (on this list the countdown; History T-028 puts the Immich album button there); the footer area is drawn only when the host supplies one, so a card without a footer shows nothing extra (`TripCard.svelte:262-267`). A trip without a start date (`formatDateRange` returns an empty string) draws no meta line at all: no date range, no route and no content chips (`TripCard.svelte:218-228`); an end date alone is ignored.
  - Route: the typed origin place, else the origin airport; the first listed destination's name, else the destination airport; shown as `from → to` plus ` +N` for N extra destinations when both exist and differ, else just `from`.
  - Content chips: flights (kept as "0 flights" only when the trip has no legs, stays or rentals at all), ground legs (named by type, e.g. train, bus, ferry, car, only when all legs are one kind, otherwise a glyph per kind and the generic "legs" label). Glyphs of a mixed trip are always in the fixed order train 🚆, bus 🚌, ferry ⛴️, car 🚗 (not row order); a segment type that is none of those four gets the neutral glyph "↔". A single-kind trip (exactly one distinct known type in `segment_types`) uses `trips.segment_count_<type>` (e.g. `trips.segment_count_bus` "{n} bus"; plural twin when n is not 1, e.g. `trips.segment_count_ferry_plural` "{n} ferries"); anything else uses `trips.segment_count` ("{n} legs"), stays, car rentals, people (only when there are collaborators, guests or pending invites; people = collaborators + guests + 1) and a separate pending-invites chip (`trips.pending_invite_count` "{n} invite pending", plural twin `trips.pending_invite_count_plural` "{n} invites pending"; `TripCard.svelte:128`). Plural keys follow T-004.
  - Stars (container accessibility label `trips.rating_label`, "Trip rating"; `TripCard.svelte:237`): five stars, filled 100/50/0 percent for each (half stars allowed), shown on the list only when the trip has a rating.
  - Expense totals: one pill per currency from `trip.expenses_total`, sorted (T-008).
  - Budget alarm: only when spent is at or above 80 percent of the budget and the budget has a currency (`budgetLevel` near or over); line "🎯 {spent} / {amount}" where each side is the `formatCurrencyTotals` string "CODE number" (T-008), for example "🎯 EUR 850 / EUR 1,000", styled by level (`near` from 80 percent up to below 100, `over` at 100 percent or more, per `budgetLevel`, T-027: 700 of an 800 budget is near, 800 of 800 is over); a trip with no `budget_amount` (null) or an amount of 0 or less shows nothing; `budget_spent` defaults to 0; nothing is shown without `budget_currency`; it ignores whether the trip has started (`TripCard.svelte` 171-182). Nothing is shown below 80 percent.
- Status pill: upcoming or ongoing (the completed pill exists in the card but never appears on this list). Upcoming trips with a start date also show the countdown from `timeUntilTrip` (T-008), refreshed every 60 seconds. Ongoing shows no day counter. When `timeUntilTrip` returns an empty string (start instant already passed, which can happen in the last hours before a trip in zones behind UTC because it counts to 00:00 UTC) no countdown element is drawn at all (`TripsListPage.svelte` 223-224, `TripCard.svelte` 240). Status pill text: `trips.upcoming` "Upcoming", `trips.ongoing` "Ongoing", `trips.completed` "Completed" (never shown here).
- Cover images come from `GET /api/trips/{id}/image`. If an image fails to load, the page asks `POST /api/trips/{id}/image/refresh` once for that trip, then adds `?t=<timestamp>` to that trip's image URL to reload it; if the retry also fails (or the refresh errors) the card shows a plane glyph instead. The timestamp is kept in memory (shared with the trip page) until the app reloads. There is no manual refresh control on the list card (it lives in the trip detail, T-010).
- Sync status bar (above the list, not shown while loading or on error): a status dot (running, error, else idle) and text, first match wins (`SyncStatusBar.svelte:21-62`): (1) status running: `Syncing… — {processed} / {total} emails` when `emails_total > 0` (processed defaults to 0), else `Syncing…`; (2) status error: `Sync error: <last_error or empty>` (not "Error:"); (3) `last_synced_at` present: `Last sync: <formatDateTimeLocale(last_synced_at)>` followed, when `sync_interval_minutes` is set, by a 60%-opacity suffix in parentheses: `(in {rel} at {HH:mm})`, where rel is `{h}h {m}m` or `{m}m` under one hour and HH:mm is the device 2-digit locale time of next = last_synced_at + interval; or `(any moment)` when next is not in the future or `round(ms/60000)` is under 1; (4) otherwise `Never synced`. Precedence: running wins over error; error shows only when not running; last-sync shows only with a `last_synced_at`; a null status (status call failed) shows `Never synced`. Same component and strings as T-033. Keys: `sync.running`, `sync.running_progress`, `sync.error`, `sync.last_sync`, `sync.next_sync`, `sync.next_at`, `sync.any_moment`, `sync.never`. The suffix is computed at render time, not on a timer. It is shown for every server; the web has no demo-mode hiding. Two buttons sit in the bar:
  - "Upload email" (`trips.btn_upload_eml`, English text "Upload .eml"): disabled while uploading, shows a spinner instead of the label (`trips.eml_uploading` "Importing…" exists but is never shown). Opens a file picker for `.eml` and `message/rfc822`, multiple files. Each tap clears the previously chosen file before opening the picker, so choosing the same file again uploads it again (101-105). `POST /api/sync/upload-eml` multipart, field `files` repeated. If flights created/updated, stays created and cancelled are all 0 an info toast `trips.eml_none_found` ("No flights or stays found in the uploaded file(s)"); otherwise a success toast joining with " · " the parts: `trips.eml_result` ("{created} flight(s) added, {updated} updated"; only when created or updated is above 0), `trips.eml_stays` ("{count} stay(s) added"; stays above 0), `trips.eml_cancelled` ("{count} flight(s) cancelled"; cancelled above 0); then the list is reloaded. If that reload fails, the failure goes to the same catch, so an error toast `trips.eml_error` ("Upload failed: <message>") follows the success toast and the old list stays (134-139). An error shows an error toast `trips.eml_error` ("Upload failed: {error}") with the message.
  - "Sync now" (`trips.btn_sync`, English text "↻ Sync"; disabled while a sync is running or starting, spinner): `POST /api/sync/now`; success toast "Sync started!", error toast "Sync failed: <message>" (both English only). After success it polls `GET /api/sync/status` every 2 seconds, updating the bar, until status is not `running`, or until a poll finds status still `running` after more than 60 polls (the stop test is `polls > 60`, so the 61st poll is the last, about 2 minutes; 59-78); on that last poll, status `idle` still reloads the list, status `running` does not. A failed status or list request stops polling silently. Leaving the page stops the poll.
- The web has no pull-to-refresh on this screen; the list reloads only on Retry, after an upload, and after a sync that ends idle. Offline, the service-worker cache serves the last list (T-003).

## API calls
- Payload read by the card: `GET /api/trips` items carry, besides the T-005 fields, `flight_count`, `segment_count`, `stay_count`, `car_rental_count` (card chips), `segment_types: string[]` (ground types of the legs), `collaborator_count`, `pending_invite_count`, `guest_count` (people chips), `booking_refs: string[]`, `origin_place`, `origin_airport`, `destinations[].name`, `destination_airport`, `budget_amount`, `budget_currency`, `budget_spent`, `expenses_total: {CODE: number}`, `rating`, `immich_album_id`, `is_owner`, `owner_username`, `search_index` (`api/types.ts:52-96`). All counts are optional and default to 0.

- `GET /api/trips` (tripsApi.list)
- `GET /api/trips/{id}/image` (tripsApi.imageUrl; optional `?t=`)
- `POST /api/trips/{id}/image/refresh` (tripsApi.refreshImage, automatic, once per trip after an image error)
- `GET /api/sync/status` (syncApi.status; also polled after Sync now)
- `POST /api/sync/now` (syncApi.now)
- `POST /api/sync/upload-eml` (syncApi.uploadEml)

## Android notes

Accept `.eml` files with `ActivityResultContracts.OpenDocument` (MIME `message/rfc822`, also `*/*` because some providers label them octet-stream). Also register an `ACTION_SEND` intent filter for `message/rfc822` so a user can share an email from Gmail straight into Partiu; the web manifest has no share target, so this is new native behaviour and optional for first release. Images: Coil.

## iOS notes

Use `fileImporter` (Files app, `UTType.emailMessage`) for `.eml`. A Share Extension that accepts an email attachment is the native equivalent of forwarding; it needs an App Group to hand the file to the main app or upload directly with the stored session. Images: Nuke or AsyncImage with a disk cache.
