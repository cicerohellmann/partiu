## What it does

Gates: the VAPID status block is shown only to admins (`is_admin`); the Notifications block is shown to all signed-in users. There is no demo gate.

Admin VAPID status (admin only):
- On page open (admins only) `GET /api/notifications/vapid/status` returns `{configured, source, public_key}`. Shows a dot (green when configured, amber otherwise) and text: "Ready — VAPID keys configured (from environment)" or "(auto-generated)" (`settings.push_ready` "Ready — VAPID keys configured ({source})", with `settings.push_source_env` / `settings.push_source_auto`), or `settings.push_not_ready` ("VAPID keys not yet generated — restart the server to auto-generate them"). A failure is ignored. The web never calls `POST /api/notifications/vapid/generate` (it exists in the client but no screen uses it; keys are generated by the server at startup).

Notifications block (all users; heading `settings.notif_title` "Notifications", `SettingsPage.svelte:1145`; the admin block above it is headed `settings.push_title` "Push Notifications", line 1131), by browser state from `getStatus()`:
- `unsupported` (no service worker, Push API or Notification API): text "Push notifications are not supported in this browser."
- `denied` (browser permission blocked): text "Notifications are blocked by your browser. Reset the permission in your browser settings to enable them."
- otherwise: a description ("Get push notifications for upcoming flights, check-in reminders, and trip start alerts.") and a button "Enable push notifications" (when not subscribed) or "Disable push notifications" (when subscribed), disabled with `settings.notif_toggling` ("…") while working.
- Status (`getStatus`, `notifications.ts:15-17, 30-38`) is decided in this order: unsupported (no service worker, Push API or Notification API), then denied, then subscribed (a push subscription exists), then unsubscribed (permission granted, no subscription), else default (not asked yet). Default and unsubscribed both show the "Enable push notifications" button; only subscribed shows "Disable" and the preferences form; preferences are fetched for subscribed and unsubscribed (`SettingsPage.svelte:332-340`). Native mapping: unsupported = no push capability, denied = OS permission denied, subscribed = permission granted and device token registered, unsubscribed = permission granted and no token, default = not asked.
- Library rules (`notifications.ts:21-23, 66-73`): `isSupported()` is true only when the service worker, Push API and Notification API all exist. `subscribe()` returns `false`, without throwing and without any request, when push is not supported or the permission prompt is not answered with "granted"; it returns the result of the key fetch and subscription otherwise. `getStatus()` always returns one of `unsupported`, `denied`, `default`, `subscribed`, `unsubscribed`.
- Enable: first `GET /api/notifications/vapid-public-key`; if that fails the message is "Push notifications are not configured on this server yet" followed by `settings.notif_not_configured_admin` (" — generate VAPID keys above.") for admins or ". Contact your admin." for others, and nothing else happens. Then the browser permission is requested; if refused: `settings.notif_permission_error` ("Could not enable notifications — check browser permissions"). If granted, the browser subscribes with the server key and the subscription is sent with `POST /api/notifications/subscribe` `{subscription}` (the browser's subscription JSON). Only after the server accepted the subscription is the local flag `partiu_push_enabled` = `1` stored (`notifications.ts:60-80`); native stores its "push enabled" flag only after the token POST succeeds. Success: "Push notifications enabled"; the status is re-read and, if subscribed, preferences are loaded with `GET /api/notifications/preferences`.
- Disable: the browser subscription is removed and `DELETE /api/notifications/subscribe` is sent with body `{endpoint}`; message "Push notifications disabled". Local flag `partiu_push_enabled` is removed first, before the network calls; with no existing subscription Disable still succeeds with "Push notifications disabled" (`notifications.ts:90-105`). Native clears its flag first on disable.
- Preferences: shown only while subscribed (also loaded at page open when the status is subscribed or unsubscribed; a load failure is ignored and the defaults stay on). Under the heading `settings.notif_what` ("What to notify"), six checkboxes, all on by default, keys `flight_reminder` (`settings.notif_flight_reminder` "Flight reminder (2 hours before departure)"), `checkin_reminder` (`settings.notif_checkin_reminder` "Check-in reminder (24 hours before departure)"), `trip_reminder` (`settings.notif_trip_reminder` "Trip reminder (1 day before trip starts)"), `delay_alert` (`settings.notif_delay_alert` "Delay & cancellation alerts (when departure is delayed ≥15 min or cancelled)"), `boarding_pass` (`settings.notif_boarding_pass` "Boarding pass ready (when a boarding pass is automatically added to a flight)"), `new_flight` (`settings.notif_new_flight` "New flights found (when new flights are added from your emails)"). A "Save preferences" button (shows "Saving…") sends `POST /api/notifications/preferences` with the six booleans; message "Preferences saved". A "Test" button (shows `settings.notif_testing` "…" while the request runs) sends `POST /api/notifications/test`; the answer `{ok, sent}` gives "Test notification sent!" when `ok`, otherwise "No subscriptions found" (shown in red). Errors from either show the server message in red. All messages share one line below the block. Each of the three actions (enable/disable, save preferences, Test) first clears that line. Any exception in the enable/disable flow, including the status or preferences re-read after it, shows its message in red; success is green. The line sits below the block and exists only in the normal state (not unsupported, not denied); `SettingsPage.svelte:347-386, 1210-1216`.
- On app start, if the user had enabled push (`partiu_push_enabled` flag) and the permission is still granted but the browser subscription is gone, `restoreIfNeeded` re-subscribes silently; if the permission was revoked the flag is cleared. Failures are ignored.
- What the browser shows (`sw.js`): a push payload `{title, body, url, badge?}` (defaults title "Partiu", url "/"). It shows a system notification with the app icon, and sets the app badge to `badge` when that is a number. A push with no body at all is dropped silently (`sw.js:196-197`); a body that is not JSON is shown with its raw text as the notification body and the default title; JSON fields override the defaults `{title: "Partiu", body: "", url: "/"}` field by field (`sw.js:199-206`). Tapping it closes it, then reuses the running app window (focus, and tell it to navigate to `url`) or opens a new window at `url` if none is open (`sw.js:228-245`).
- Badge clearing (`App.svelte`, also described in T-031): after sign-in is known and every time the page becomes visible while signed in, the app clears the OS badge when the platform supports it and sends `POST /api/notifications/badge/clear` (failure ignored).
- Texts the server sends (the push `title`/`body` that `sw.js` shows; the same text is also stored as an in-app notification). The server writes them in the user's saved language (`users.locale`, default "en"; `push_repository.get_locale`, `reminder_job.py:31-39`, `routes.py:177`), using the `notif.*` keys in its locale files. Placeholders in braces:
  - Flight reminder, `reminder_job.py:91-97`, departure 1h50 to 2h20 away and `flight_reminder` on: `notif.flight_reminder_title` ("Flight {flight} in ~{mins} min"), `notif.flight_reminder_body` ("{from} → {to}"); url is the trip or home.
  - Check-in reminder, `reminder_job.py:111-113`, departure 23 to 25 h away, `checkin_reminder` on: `notif.checkin_title` ("Check-in open: {flight}"), `notif.checkin_body` ("{from} → {to} — departs tomorrow").
  - Trip reminder, `reminder_job.py:144-145`, trip start 23 to 25 h away, `trip_reminder` on: `notif.trip_reminder_title` ("Trip tomorrow: {name}"), `notif.trip_reminder_body` ("Your trip starts tomorrow. Have a great journey!").
  - New flights after a sync, `sync/pipeline.py:969-970`, `new_flight` on and at least one flight created: `notif.new_flights_title` ("New flights added ✈"); body `notif.new_flights_body` when `{n}` is 1 ("{n} new flight added from your emails.") or `notif.new_flights_body_plural` when `{n}` is more than 1.
  - Departure moved, `pipeline.py:442-444`, `delay_alert` on, once per new departure time: `notif.rescheduled_title` ("Flight {flight} rescheduled"), `notif.rescheduled_body` ("{from} → {to}: now departs {new}, was {old}"; times in the flight's time zone).
  - Airline schedule-change mail, `pipeline.py:509-510`, `delay_alert` on: `notif.schedule_change_notice_title` ("Schedule change: booking {ref}"), `notif.schedule_change_notice_body` ("{airline} changed the schedule of this booking. Check the new itinerary in the airline's email or app.").
  - "Test" button, `routes.py:181-182`: `notif.test_title` ("Partiu — test notification"), `notif.test_body` ("Push notifications are working!").
  Plural rule: only the new-flights body; singular for exactly 1, plural otherwise (two keys, no ICU).

## Tests

- Status test: an admin sees the VAPID line for `configured` true with source `env` and `auto`, and for `configured` false; a non-admin never calls `GET /api/notifications/vapid/status` and sees no block.
- Preferences test: with six prefs from `GET /api/notifications/preferences` the checkboxes match; unchecking `delay_alert` and saving posts all six booleans with `delay_alert: false` and shows "Preferences saved"; a failed save shows the server message.
- Test-button test: `{ok: true}` shows "Test notification sent!"; `{ok: false}` shows "No subscriptions found".
- Not-configured test: when the public-key call fails, enabling shows the "not configured" message (admin and non-admin variants) and no subscribe request is sent.
- Badge test: after sign-in and on each return to the foreground, `POST /api/notifications/badge/clear` is sent once and its failure is ignored.
- Payload test: a non-JSON push body shows the title "Partiu" and the text as body; a JSON payload with only `body` keeps the default title; an empty push shows nothing.
- Tap test: tapping a notification with a trip `url` opens that screen (reusing the running app); tapping one with no `url` opens the Inbox/Trips root.
- Push text test: for a user with locale pt-BR and one with no locale, each event above produces the matching `notif.*` title and body in that language (English by default) with placeholders filled; new flights gives the singular body for 1 and the plural for 2.
- Notifications heading test: the Settings screen shows a block headed "Notifications" for every signed-in user (web test: "renders notifications section").
- Push status block test: for an admin whose `GET /api/notifications/vapid/status` answers `{configured: true, source: "auto"}` the block headed "Push Notifications" is shown (web test: "shows admin-only Push Notifications section for admin user").
- Status value test: when the device cannot do push the status is `unsupported`; in every other case the status is one of `denied`, `default`, `subscribed`, `unsubscribed` (web test: "getStatus returns unsupported in test environment").
- Subscribe unsupported test: with no push capability, `subscribe()` returns false, does not throw and sends no request (web test: "subscribe returns false when not supported").
Web tests mirrored: frontend/src/pages/SettingsPage.test.ts, frontend/src/lib/notifications.test.ts

## Native additions (not in web)

The web uses browser Web Push only (VAPID keys; `pywebpush` on the server side is not part of the web sources reviewed here). A native app cannot use a browser subscription, so this needs a backend change, which is a proposal and not existing behaviour:

- Native push (FCM and APNs) must deliver exactly the same title and body the web push sends (same `notif.*` text in the user's locale, same `url`).
- Backend: an endpoint to register a device token (token, platform `fcm` or `apns`, app version) per user; a sender that pushes each event the web already pushes through FCM and APNs too; the same six preferences honoured; tokens the push service reports as invalid are removed. iOS needs an APNs auth key (`.p8`) on the server.
- App: ask for notification permission from the settings toggle (not at launch); register the token after sign-in and delete it at sign-out; keep the same preferences screen, "Test" button and messages as above; clear the badge when the app opens; open the related trip (payload `url`) or the Inbox (T-031) when a notification is tapped.
- The web-only calls (`vapid-public-key`, `subscribe`) are not used by the native app once the new endpoint exists.
- Android: FCM SDK, a `NotificationChannel` per kind of event, `POST_NOTIFICATIONS` permission on Android 13 and later, token refresh in `FirebaseMessagingService`, deep link with a `PendingIntent`.
- iOS: Push Notifications capability, `registerForRemoteNotifications`, send the device token to the backend, handle taps in `UNUserNotificationCenterDelegate`, badge through `setBadgeCount`.
- Native tests: after sign-in the token is posted once with its platform and deleted at sign-out; a notification carrying a trip url opens that trip and one without opens the Inbox; a backend test pushes a flight change through Web Push, FCM and APNs for a user who has all three.
- Message line test: starting any of the three actions clears the previous message; a failing preferences re-fetch after enabling shows its message in red; in the unsupported and denied states no message line is drawn.
- Status order test: denied wins over a stored token; token present gives subscribed; permission granted without token gives unsubscribed; never asked gives default.
- Flag test: the enabled flag is stored only after the token POST succeeds; Disable removes it first and still reports success when no token exists.
